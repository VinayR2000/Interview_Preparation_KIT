# 21. Idempotency ⭐⭐⭐

---

## Theory

**Idempotency** means that performing an operation multiple times has the same effect as performing it once. In Kafka, this applies to both producers (no duplicate writes) and consumers (safe reprocessing).

### Idempotent Producer

```
enable.idempotence = true (default since Kafka 3.0)

Mechanism:
- Producer gets PID (Producer ID) from broker
- Each record assigned sequence number per (PID, partition)
- Broker tracks: last sequence number for each (PID, partition)
- Duplicate detection: if sequence already recorded → ack without writing

Without idempotence:
  send() → timeout → retry → DUPLICATE in log!

With idempotence:
  send() → timeout → retry → broker sees same seq → returns success (no duplicate)
```

### Duplicate Events at Consumer

Even with idempotent producer, consumers can see duplicates:

```
Scenario 1: Consumer processes, crashes before commit
  → Restart → re-reads → duplicate processing

Scenario 2: Rebalance during processing
  → Partition reassigned → new consumer re-reads from committed offset

Scenario 3: Producer sends to multiple consumers groups
  → Each group processes independently (no producer-level dedup helps here)
```

### Idempotent Consumer

Designing consumers that safely handle duplicate messages.

```
Strategy 1: Unique Event ID
  Every event carries a unique ID (UUID or composite key)
  Consumer checks: "have I processed this ID before?"
  If yes → skip
  If no → process + store ID

Strategy 2: Database Unique Constraint
  INSERT with unique constraint on event_id
  Duplicate → constraint violation → catch and skip

Strategy 3: Idempotent Operations
  Use operations that are naturally idempotent:
  SET balance = 500  (idempotent — same result regardless of repetitions)
  ADD balance + 100  (NOT idempotent — doubles on duplicate!)

Strategy 4: Version/Timestamp Check
  Process only if event is newer than current state
  If event.version ≤ current.version → skip (stale/duplicate)
```

### Deduplication Patterns

```java
// Pattern 1: In-memory cache (simple, not durable)
Set<String> processedIds = ConcurrentHashMap.newKeySet();

public void process(Event event) {
    if (!processedIds.add(event.getEventId())) {
        log.info("Duplicate: {}", event.getEventId());
        return;  // skip
    }
    doProcess(event);
}

// Pattern 2: Database-backed (durable, production-ready)
@Transactional
public void process(Event event) {
    if (processedEventRepository.existsByEventId(event.getEventId())) {
        return;  // already processed
    }
    
    // Process event
    orderRepository.save(toOrder(event));
    
    // Record as processed (same transaction)
    processedEventRepository.save(new ProcessedEvent(event.getEventId()));
}

// Pattern 3: Conditional write (naturally idempotent)
@Transactional
public void processOrderStatus(OrderStatusEvent event) {
    // Only update if version is newer
    int updated = orderRepository.updateStatusIfNewer(
        event.getOrderId(), 
        event.getStatus(), 
        event.getVersion()
    );
    if (updated == 0) {
        log.info("Stale event, skipping: {}", event.getEventId());
    }
}
```

### Idempotency Key Design

```
Good idempotency keys:
- UUID generated by producer: event.eventId = UUID.randomUUID()
- Composite natural key: orderId + eventType + timestamp
- External reference: paymentGatewayTransactionId

Bad idempotency keys:
- Kafka offset (changes on rebalance with different consumer)
- Timestamp alone (not unique enough)
- Auto-increment (not available at produce time)
```

### Exactly-Once vs Idempotency

```
Exactly-Once (Kafka transactions):
  - Atomic consume-transform-produce within Kafka
  - Built-in mechanism (transactional producer + read_committed)
  - Scope: Kafka-to-Kafka pipelines only

Idempotency (application level):
  - Safe reprocessing at consumer level
  - Works with external systems (database, API, cache)
  - Scope: Kafka-to-anything
  - More flexible, works everywhere

In practice: Most systems use at-least-once + idempotent consumers
  → "Effectively exactly-once" semantics
```

## Code

### Complete Idempotent Consumer Pattern

```java
@Component
@Slf4j
public class IdempotentOrderConsumer {

    private final OrderRepository orderRepository;
    private final ProcessedEventRepository processedRepo;

    @KafkaListener(topics = "orders", groupId = "order-processing")
    @Transactional  // DB transaction wraps everything
    public void handleOrder(@Payload OrderCreatedEvent event,
                            @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
                            @Header(KafkaHeaders.OFFSET) long offset,
                            Acknowledgment ack) {
        
        String eventId = event.getEventId();
        
        // 1. Idempotency check
        if (processedRepo.existsByEventId(eventId)) {
            log.debug("Duplicate event {}, partition={}, offset={}", eventId, partition, offset);
            ack.acknowledge();
            return;
        }
        
        // 2. Process business logic
        Order order = Order.builder()
            .orderId(event.getOrderId())
            .amount(event.getAmount())
            .status(OrderStatus.CREATED)
            .build();
        orderRepository.save(order);
        
        // 3. Record as processed (in SAME DB transaction)
        processedRepo.save(ProcessedEvent.builder()
            .eventId(eventId)
            .topic("orders")
            .partition(partition)
            .offset(offset)
            .processedAt(Instant.now())
            .build());
        
        // 4. Commit Kafka offset
        ack.acknowledge();
        
        log.info("Processed order {}, eventId={}", event.getOrderId(), eventId);
    }
}

@Entity
@Table(name = "processed_events", 
       uniqueConstraints = @UniqueConstraint(columnNames = "event_id"))
public class ProcessedEvent {
    @Id @GeneratedValue
    private Long id;
    
    @Column(name = "event_id", unique = true, nullable = false)
    private String eventId;
    
    private String topic;
    private int partition;
    private long offset;
    private Instant processedAt;
}
```

## Interview Questions

### Q1: How is idempotent producer different from idempotent consumer?

**A:**
- **Idempotent producer:** Kafka built-in mechanism using PID + sequence numbers. Prevents duplicate writes to Kafka from retries. Handled transparently by the Kafka client. Scope: ensures each record written to broker exactly once.
- **Idempotent consumer:** Application-level pattern. Developer must implement deduplication logic (event ID tracking, conditional writes, etc.). Handles duplicate processing from at-least-once delivery. Scope: ensures each event's effects applied exactly once in external systems.

### Q2: How would you implement idempotency for a payment processing consumer?

**A:**
```java
@Transactional
public void processPayment(PaymentEvent event) {
    // 1. Check if payment already processed
    if (paymentRepo.existsByPaymentId(event.getPaymentId())) {
        return; // idempotent — skip duplicate
    }
    
    // 2. Call payment gateway (with payment ID as idempotency key)
    PaymentResult result = gateway.charge(event.getPaymentId(), event.getAmount());
    
    // 3. Store result atomically
    paymentRepo.save(Payment.from(event, result));
}
```
Key decisions: use external payment ID as idempotency key, check before calling gateway, gateway also supports idempotency keys, store in same DB transaction.

### Q3: What are the limitations of idempotent producer?

**A:**
- Only prevents duplicates within a single partition (per PID+partition)
- Does NOT prevent cross-partition duplicates
- Does NOT help with consumer-side duplicates
- PID expires after `transactional.id.expiration.ms` (7 days) if no activity
- After PID expiry + restart = new PID = duplicates possible for very old retries
- For cross-partition atomicity: need full transactions

## Best Practices

1. **Always include event ID** in messages (for consumer deduplication)
2. **Store event ID with result** in same database transaction
3. **Design idempotent operations** where possible (SET > ADD)
4. **Use database unique constraints** as safety net
5. **Clean up processed events table** periodically (retention window)
6. **Enable idempotent producer** (it's default now — don't disable it)
7. **Pair at-least-once delivery with idempotent consumers** for production systems
