# EC2 — Elastic Compute Cloud ⭐⭐⭐

## Theory

EC2 provides resizable virtual servers (instances) in the cloud. You choose the OS, instance type, storage, and networking — full control over the compute environment.

---

## Internal Working

### EC2 Instance Lifecycle

```
AMI (Template)
    ↓ Launch
Pending → Running → Stopping → Stopped
              ↓                    ↓
          Shutting-down       Starting → Running
              ↓
          Terminated (deleted)
```

| State | Billing | Data |
|-------|---------|------|
| Running | Charged | Instance store: yes, EBS: yes |
| Stopped | No compute charge (EBS charged) | EBS: persists |
| Terminated | No charge | Everything deleted |

### Key Components

| Component | Description |
|-----------|-------------|
| AMI | Machine image (OS + pre-installed software) |
| Instance Type | CPU, RAM, network, storage capacity |
| EBS | Persistent block storage (survives stop/start) |
| Security Group | Firewall rules |
| Key Pair | SSH access (public/private key) |
| User Data | Bootstrap script (runs on first launch) |
| Instance Profile | IAM Role attachment |
| Elastic IP | Static public IP (persists across stop/start) |

## Diagram

### Instance Types

```
Instance Type: t3.xlarge
               │  │
               │  └── Size: xlarge (4 vCPU, 16 GB RAM)
               └───── Family: t3 (burstable general purpose)

Common Families:
├── t3/t4g  → General purpose, burstable (dev, small apps)
├── m5/m6i  → General purpose, consistent (production apps)
├── c5/c6i  → Compute-optimized (CPU-intensive)
├── r5/r6i  → Memory-optimized (databases, caching)
├── i3      → Storage-optimized (high I/O)
└── g4/p4   → GPU instances (ML, graphics)
```

### For Spring Boot Applications:
- **Development**: t3.medium (2 vCPU, 4 GB) — good with burstable CPU
- **Production**: m5.large (2 vCPU, 8 GB) or m5.xlarge (4 vCPU, 16 GB)
- **Memory-heavy** (large caches): r5.large (2 vCPU, 16 GB)

## Code

### User Data — Bootstrap Spring Boot on EC2

```bash
#!/bin/bash
# User Data script — runs as root on first boot

# Install Java 17
yum update -y
yum install -y java-17-amazon-corretto

# Create application user
useradd -r -s /sbin/nologin appuser

# Download application from S3
aws s3 cp s3://my-deployments/myapp-1.0.0.jar /opt/myapp/app.jar

# Create systemd service
cat > /etc/systemd/system/myapp.service << 'EOF'
[Unit]
Description=Spring Boot Application
After=network.target

[Service]
Type=simple
User=appuser
ExecStart=/usr/bin/java -Xmx1g -jar /opt/myapp/app.jar --spring.profiles.active=production
Restart=on-failure
RestartSec=10
Environment=SPRING_DATASOURCE_URL=jdbc:postgresql://mydb.cluster-xxx.us-east-1.rds.amazonaws.com:5432/mydb

[Install]
WantedBy=multi-user.target
EOF

# Start application
systemctl daemon-reload
systemctl enable myapp
systemctl start myapp
```

### Terraform EC2 Example
```hcl
resource "aws_instance" "app" {
  ami                    = "ami-0c02fb55956c7d316"  # Amazon Linux 2
  instance_type          = "t3.medium"
  subnet_id              = aws_subnet.private[0].id
  vpc_security_group_ids = [aws_security_group.app.id]
  iam_instance_profile   = aws_iam_instance_profile.app.name
  key_name               = "my-key-pair"
  
  user_data = file("userdata.sh")

  root_block_device {
    volume_type = "gp3"
    volume_size = 30
    encrypted   = true
  }

  tags = {
    Name        = "spring-boot-app"
    Environment = "production"
  }
}

resource "aws_security_group" "app" {
  name   = "app-sg"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port       = 8080
    to_port         = 8080
    protocol        = "tcp"
    security_groups = [aws_security_group.alb.id]  # Only from ALB
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

## EBS (Elastic Block Store)

### Volume Types

| Type | Use Case | IOPS | Throughput |
|------|----------|------|-----------|
| gp3 | General (default) | 3,000-16,000 | 125-1,000 MB/s |
| gp2 | General (legacy) | 3,000-16,000 | Burst |
| io2 | High-performance DB | Up to 64,000 | 1,000 MB/s |
| st1 | Throughput (logs, big data) | 500 | 500 MB/s |
| sc1 | Cold storage (archive) | 250 | 250 MB/s |

**For Spring Boot**: Use gp3 (30 GB minimum for production)

### EBS Snapshots
```
EBS Volume → Snapshot (stored in S3) → New Volume or AMI
```
- Point-in-time backup
- Incremental (only changed blocks)
- Can copy across regions (disaster recovery)
- Can create AMI from snapshot

## Purchasing Options

| Option | Discount | Commitment | Use Case |
|--------|----------|-----------|----------|
| On-Demand | 0% | None | Dev, testing, unpredictable workloads |
| Reserved (1yr) | ~40% | 1 year | Steady-state production |
| Reserved (3yr) | ~60% | 3 years | Long-running baseline |
| Savings Plan | ~40-60% | $/hr commitment | Flexible across instance types |
| Spot | Up to 90% | None (can be interrupted) | Batch jobs, CI/CD, stateless |

### Spot Instances for Spring Boot
- Use for: CI/CD builds, batch processing, development environments
- NOT for: Production APIs (can be terminated with 2 min notice)
- Strategy: Mix On-Demand (baseline) + Spot (peak capacity)

## Real Project Usage

### Deploying Spring Boot to EC2 (Manual/Basic)

```
1. Create EC2 instance (private subnet)
2. Attach IAM Role (S3 read, Secrets Manager access)
3. Security Group: Allow 8080 from ALB only
4. User Data: Install Java, download JAR, start service
5. Configure ALB to route to instance
6. Health check: /actuator/health
```

### Instance Metadata Service
```bash
# From within EC2 instance — get instance information
curl http://169.254.169.254/latest/meta-data/instance-id
curl http://169.254.169.254/latest/meta-data/local-ipv4
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/MyRole
# ↑ This is how SDK gets temporary credentials from IAM Role
```

## Interview Questions and Answers

**Q: How would you deploy a Spring Boot application on EC2?**
> 1. Create AMI with Java 17 installed (or use User Data to install on launch)
> 2. Launch EC2 in private subnet with IAM Role for needed AWS services
> 3. Security group: allow port 8080 only from ALB security group
> 4. Use systemd to manage the Java process (auto-restart on failure)
> 5. Store secrets in AWS Secrets Manager (not in application.properties)
> 6. Put behind ALB with health checks on /actuator/health
> 7. Use Auto Scaling Group for high availability

**Q: What's the difference between stopping and terminating an EC2 instance?**
> Stopping: Instance is shut down, EBS volumes persist, no compute charges (EBS still charged). Can be restarted. Public IP released (unless Elastic IP). Terminating: Instance and instance-store volumes are deleted permanently. EBS volumes deleted unless DeleteOnTermination=false. Cannot be recovered.

**Q: How does EC2 get credentials when using an IAM Role?**
> Through the Instance Metadata Service (IMDS) at 169.254.169.254. The EC2 instance profile provides temporary credentials (access key, secret key, session token) that auto-rotate before expiration. AWS SDKs automatically query this endpoint — no configuration needed in your application code.

**Q: When would you use Spot instances?**
> For fault-tolerant, stateless workloads: CI/CD pipelines, batch processing, data analysis, development environments. Never for production API servers (can be terminated with 2-minute notice). Strategy: Run baseline on On-Demand/Reserved, use Spot for burst capacity in Auto Scaling Groups with mixed instance types.

## Common Mistakes

1. **Running in public subnet without ALB** — Always use private subnet + ALB
2. **Not using IAM Roles** — Never hardcode credentials on EC2
3. **Single instance without Auto Scaling** — No HA, no self-healing
4. **gp2 when gp3 is better** — gp3 is cheaper with predictable performance
5. **Not enabling detailed monitoring** — 1-minute intervals needed for responsive scaling
6. **Over-provisioning instance size** — Start small, scale up based on metrics

---

## Best Practices

1. **Use private subnets** for application instances
2. **Attach IAM Roles** — never store access keys
3. **Use Auto Scaling Groups** even for single instances (self-healing)
4. **Encrypt EBS volumes** at rest
5. **Use gp3** as default volume type
6. **Create golden AMIs** with Java + monitoring agents pre-installed
7. **Enable IMDSv2** (Instance Metadata Service v2) for security
8. **Tag everything** for cost allocation and management
